4.1. Objetivo

Automatizar pruebas de integración que permitan consultar productos de Fake Store API, validar los datos
recibidos y comprobar su almacenamiento y recuperación mediante SQLite en memoria. Además, evaluar
escenarios de error y la consistencia de los datos durante el flujo de integración.

4.2. Preparación del entorno

Para desarrollar las pruebas se utiliza Python, Pytest y Requests. La biblioteca SQLite está incluida en
Python y permite crear una base de datos temporal sin instalar un servidor adicional. El proyecto utiliza
un entorno virtual para administrar sus dependencias.







Imagen 14. Verificación del entorno de pruebas y disponibilidad de las dependencias.

4.3. Organización del proyecto

El proyecto contiene una carpeta tests para las pruebas automatizadas, una carpeta evidencias para los
resultados de ejecución y un archivo requirements.txt con las dependencias necesarias.












Imagen 15. Estructura del proyecto de automatización.

4.4. Configuración de SQLite en memoria

La conexión se configura mediante una fixture de Pytest utilizando sqlite3.connect(":memory:"). Cada
prueba que solicita esta fixture recibe una base de datos nueva, con una tabla para almacenar los
productos del carrito. Al finalizar la prueba, la conexión se cierra y los datos temporales se eliminan.

5. Ejercicios adicionales

5.1. Idempotencia y control de duplicados

Se repite el almacenamiento del mismo producto con idénticos datos y cantidad para comprobar que el
estado del carrito se mantenga sin cambios. Se utiliza una restricción UNIQUE sobre producto_id y una
operación de inserción con actualización en caso de conflicto.

Regla implementada: Cada producto puede ocupar una sola fila en el carrito. Al guardar nuevamente el
mismo identificador, se reemplazan sus datos y cantidad. La cantidad recibida representa la cantidad final
deseada, por lo que no se acumula con la anterior.

verifica que la operación no se anuncie como exitosa y que el carrito permanezca vacío.

9. Conclusiones

Con este laboratorio pudimos comprobar que probar una API no consiste solamente en revisar que
devuelva un código HTTP exitoso, sino también en verificar los datos y cómo se utilizan durante el flujo.
Con Postman exploramos las solicitudes y sus respuestas, mientras que con Pytest automatizamos las
consultas, el almacenamiento en SQLite y las comprobaciones del carrito. En la ejecución final aprobaron
14 de las 15 pruebas, para un 93,33 % de aprobación. La prueba fallida permitió identificar que la API
aceptaba cantidades negativas, aunque respondía con HTTP 201. Esto demuestra que algunos problemas
podrían pasar desapercibidos si solo revisamos la interfaz gráfica o los códigos de respuesta.

También comprobamos que los productos se almacenaban y recuperaban correctamente, que el total del
carrito coincidía con lo esperado y que repetir el almacenamiento no generaba duplicados. Al provocar un
fallo de escritura, el código informó el error sin anunciar una operación exitosa. La automatización nos
permitió repetir estas comprobaciones y conservar evidencia de los resultados. Aun así, trabajamos con

solicitudes repetidas o fallos de un proveedor de pagos, por el riesgo de generar cobros duplicados o
pedidos inconsistentes.



9.1. Respuestas a las preguntas finales de la guía

¿Qué diferencia observó entre una prueba de API aislada y una prueba de integración?
Una prueba aislada comprueba una solicitud y su respuesta, por ejemplo, el código HTTP y los campos de
un producto. Una prueba de integración verifica la interacción entre componentes. En este laboratorio se
consultó la API, se almacenaron sus datos en SQLite y se recuperaron para comprobar su consistencia. El
fallo de escritura simulado demostró que una respuesta correcta de la API no garantiza que todo el flujo
termine correctamente.

¿Qué defectos podrían pasar desapercibidos si solo se prueba la interfaz gráfica?
Podrían pasar desapercibidos la aceptación de cantidades negativas mediante solicitudes directas, los tipos
de datos incorrectos, las respuestas ambiguas para recursos inexistentes y los problemas de persistencia.
Una interfaz puede impedir ciertas entradas, mientras que la API continúa aceptándolas cuando se
consulta directamente.

¿Qué validaciones fueron más importantes: estado HTTP, contrato JSON, reglas de negocio o
persistencia? Justifique.

Las reglas de negocio y la persistencia fueron especialmente importantes para evaluar el flujo completo.
La API respondió HTTP 201 ante una cantidad negativa, por lo que un código de éxito no garantizó datos
válidos. Asimismo, las consultas posteriores a SQLite permitieron comprobar el almacenamiento real
dentro de la prueba. El estado HTTP y el contrato JSON siguen siendo necesarios para interpretar la
respuesta y procesarla correctamente.
¿Qué riesgos tendría integrar un proveedor externo de pagos sin pruebas automatizadas?

Podrían producirse cobros duplicados al repetir solicitudes, montos incorrectos, estados de pago mal
interpretados o diferencias entre el pago y el pedido registrado. También sería más difícil detectar
cambios del proveedor y comprobar el comportamiento ante interrupciones. Estos riesgos no se evaluaron
con pagos reales en este laboratorio, pero justifican probar la integración en un ambiente de pruebas antes
de utilizarla en producción.

¿Qué mejoraría en su estrategia de pruebas si este proyecto fuera para producción?
Incorporaría pruebas automáticas en el proceso de integración continua, ambientes controlados y
simulaciones del proveedor para escenarios de error. Ampliaría la evaluación de autenticación,
autorización, concurrencia, límites e idempotencia. Para importes monetarios utilizaría decimales o
unidades mínimas enteras. También definiría el inventario completo de endpoints y realizaría mediciones
=== PÁGINA 45 ===
repetidas de rendimiento, complementadas con pruebas de carga y seguimiento de los defectos
encontrados.
